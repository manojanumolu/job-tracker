# M7 implementation and controlled rollout

Implementation branch: `feature/m7-workday-recovery-plan`. This is uncommitted local implementation, not a deployed recovery. The planning document remains the historical specification; the decisions below describe the implemented behavior.

## Implemented behavior

* The production scraper entry point enables a single run-scoped Workday controller. Global/host spacing covers API listings, details, sitemap and job pages. Requests identify the tracker explicitly and never follow redirects automatically. Other source adapters retain their own request policies.
* HTTP 429 and retryable server/network failures have bounded backoff. Retry-After accepts seconds or HTTP-date; valid long waits become durable cooldowns. A host circuit stops later requests and repeated source sites (including both PwC sites). Three distinct throttled API hosts stop further API attempts in that run; JioStar sitemap traffic is not part of that aggregate breaker.
* Forbidden, authentication and unexpected redirects require configuration review even after the timestamped cooldown expires. There is no automatic browser fallback or alternate identity.
* Known recorded 429s receive a conservative three-hour cooldown on first deployment. Cooldown survives subsequent runs. Expired cooldown admits one controlled trial; repeated failure increases the fallback pause to 6/12/24 hours.
* The persistent cache stores definitive verdicts with bounded public posting evidence. Warm hits avoid detail requests but rerun the current classifier/safety gates, preserving skills and M6 requirements. Fingerprints, source configuration, code-derived rule/extraction version and 24-hour TTL invalidate stale entries. Hits do not extend TTL. Unknown/unreadable results are not negative cached.
* New and visibly changed postings receive priority, with one aged pending/revalidation item per three new items to prevent starvation. Pending identity hashes and first-deferred times persist. A complete later listing may remove pending entries for postings no longer present; failed/partial listings cannot do so. Schema/size bounds can evict cached evidence, never seen-job or delivery history.
* Full mode selects up to nine Workday API companies by oldest actual attempt, excluding cooldown/policy blocks. JioStar and the other existing non-API sources run first on every window, outside API rotation. Twenty-four-hour success breaches are flagged; old attempts receive scheduling priority without allowing permanently failing portals to monopolize every slot.
* No-request deferrals preserve `last_checked`, `last_success` and failure streaks. Partial/rate-limited scans cannot advance success. A completed orchestration marker is projected into `scan.run` so the scheduler and UI share the same existing company snapshot, including all-cooling windows. This deliberately avoids a second scheduler/app snapshot dependency; the authoritative safety state also records the run.
* Structured company diagnostics include method, HTTP status, host, failure category, parsed Retry-After, last attempt/success, cooldown, pending age and cache counts. Health severity counts unresolved failures even while deferred/cooling; 25% or five companies is degraded, 50% is critical. Coverage age/unknowns are reported separately. Account-specific monitoring scopes remain intact.
* GitHub Actions receives safe aggregate summaries and warnings. Portal failure does not stop valid job publication or existing alerts. Workflow success does not claim recovered portal coverage.

Documentation: this report, `docs/M7_WORKDAY_MONITORING_RECOVERY_PLAN.md`, and operational monitoring/security notes. No existing production JSON files are edited. The following files are generated by an approved scanner execution in its separate data checkout:

* `data/workday_scan_state.json`: host cooldowns, company/source scheduling observations and pending references.
* `data/workday_verdict_cache.json`: derived, bounded verdict/evidence cache.

The scrape artifact explicitly includes both alongside companies and seen jobs. Handoff validates closed schemas, bounds, safe host identities and a matching run generation before copying. The company run marker must match the state/cache generation. All four are included in the initial merge-safe publication before any alert can send; subsequent sending/finalization publications remain ledger-only. New files are never imported or executed.

Remote state merges per host/company/evaluated entry. Older observations cannot clear newer cooldowns or overwrite newer cache entries. Pruning uses the merged generation. Company merges preserve remote membership/configuration and reject old-source/stale scan results. Existing shared ledger CAS, uncertain delivery handling and personal Firestore delivery code are unchanged.

Missing cache is a cold start; corrupt cache rebuild is reported internally. Missing safety state after an M7 run or corrupt safety state stops Workday requests and refuses publication rather than erasing an unknown cooldown. Restore the last valid safety file before resuming publication. Unsupported/corrupt remote schemas are likewise refused, not overwritten. This failure intentionally prioritizes safe publication over availability and requires operator attention. No automatic production data reset is included.

## Selected settings

The checked-in trusted configuration is the source of defaults. It is not loaded from a career site or data artifact.

| Setting | Value |
|---|---|
| Default rollout | `canary` |
| API canary IDs | `sanofi`, `pwc` (existing configured API integrations; no new access claim) |
| Full rotation batch | 9 API companies |
| Global / host spacing | 1 / 2 seconds, no bursts |
| Delay between Workday companies | 10 seconds |
| Retries | 2 retries after initial request |
| Backoff / total retry waiting | 30s, 60s / maximum 120s |
| Fallback cooldown | 3h, 6h, 12h, maximum 24h; longer valid Retry-After wins |
| API aggregate breaker | 3 distinct hosts throttled in the run |
| Workday request/time ceilings | 900 requests / 1,800 seconds |
| Whole-run Workday start deadline | 4,800 seconds from orchestration start, leaving margin before the 90-minute job timeout |
| Cache TTL / entry limit / file bound | 24h / 10,000 / 16 MiB |
| Overdue success safeguard | 24h |
| Existing scan and alert schedules | Unchanged |

`JT_WORKDAY_MODE=canary|full|paused` is the sole runtime mode override. Unknown modes fail instead of widening scope. Default canary mode deliberately defers the other 24 failing APIs. Full mode's nominal revisit is `ceil(26/9) × 3h = 9h`; cooldowns, request budgets and delayed workflow starts can exceed it. Invisible detail changes are detected on TTL revalidation, not instantly. Cache/pacing limits remain enabled when rotation mode changes.

## Alternative sources: honest evidence status

JioStar's existing sitemap adapter and canonical identities are retained. New Workday sitemap mappings require explicit recent policy evidence (terms permission, robots content publishing the sitemap and allowing required paths). This is an offline gate, not a verifier of assertions: an operator must independently establish the policy. No live probes were performed.

Sanofi and PwC are the two assessment candidates because the repository already has an explicit Sanofi source and two distinct PwC career sites. **Neither has a newly verified permitted alternative.** Their alternative-source status is “requires configuration/policy verification”; their existing API integrations form the canary. Existing public-feed support for ADP/ServiceNow is preserved; it is not evidence of a Workday employer feed. No invented sitemap or feed endpoints were activated. A newly configured sitemap without sufficient evidence is deferred as `needs_config`, not shown as recovered.

## Canary, approvals and rollback

1. Review the local diff and validation results. Explicitly approve committing/pushing this branch and opening an implementation PR. No commit/push/PR has been performed in this task.
2. Review the PR's security changes, runtime limits and pending-work behavior. CI must pass before merge. Confirm the actual production environment branch rules and `JT_DATA_BRANCH` setting; these live settings were not queried or changed.
3. Separately approve merge/deployment and the first production canary scan. Merging scanner code can affect the next scheduled run, so schedule this approval before merge; do not assume merge is isolated from production. Keep default canary mode. Existing source selection and all shared/personal alert settings remain unchanged.
4. The first approved scan bootstraps cooldown from saved 429 evidence and may attempt no failing APIs. It should still scan the 18 previously active sources and publish the two new state files through the normal trusted boundary. Validate published generation, truthful health, no leaked headers and unchanged alert ledgers.
5. After cooldown, observe Sanofi/PwC outcomes, request count, last_success, cache misses/hits, pending age and run duration. Do not infer success from workflow exit status. Observe at least 48 hours/two TTLs and verify healthy-source behavior and recipient isolation. If access is forbidden or needs review, do not clear the block to force requests.
6. Obtain explicit approval to change trusted rollout mode to `full`; nine-company batches then apply. No scheduler or alert cadence changes are needed. Observe a complete rotation and report each company's actual last successful discovery. If the common limit persists, keep the health critical and assess permitted alternatives under separate live-policy authorization.
7. Emergency rollback: approve `JT_WORKDAY_MODE=paused` in the scraper environment or set trusted config mode to `paused` in a reviewed code change. This pauses API selection while JioStar/other existing scanners continue; it does not erase state. The workflow presently uses the checked-in mode, so an environment override requires an explicit workflow/environment change.
8. Cache rollback: set trusted `cache_enabled=false`; retain pacing/cooldowns. For a code rollback, revert producer, handoff and initial-publication changes together. Never restore old `seen_jobs.json` or Firestore delivery data. Preserve or restore only a validated safety-state file from data history; any policy-block reset requires new permission evidence.

No source recovery is claimed until those approved observations occur. Remaining external blockers are live rate-limit behavior, current access policies for two alternative sources, and actual production branch/environment configuration. The implementation cannot guarantee a provider permits requests merely because mocked tests pass.
